# 改动记录（排查用）

**这份文档的用法**：动手改代码前先在这里搜一遍相关模块，看清"这里已经改过什么、为什么这么改、当时实测数字是多少"，避免把已经踩过的坑再踩一遍。每完成一个有实际影响的改动（性能、交互、数据结构、构建），在顶部追加一条。

**每条记录必须包含**：现象 → 实测数据（含测试条件与数据来源）→ 根因 → 改了什么（文件:行）→ 验证结果 → 遗留与风险。没有实测数字的归因一律写成"推测"，不要写成结论。

**提交口径**：本文件随代码一起提交（属于"影响后续排查的工程记录"，不算过程垃圾文档）。

## 2026-10-20（更晚）· 把"要不要全屏沉浸"变成她的设置项 + 开机页进入按钮在 Edge 被裁掉

**现象**（两条，都是用户 2026-10-20 实测反馈）：
1. 上一轮"锁不住就退出全屏"上线后，她用探针的一键 A/B 确认：「点击了禁止全屏请求就可以一直竖着，虽然包含了地址栏」。即扳机坐实，但她得在"竖屏但带地址栏"和"沉浸但有转横风险"之间二选一，且只能靠试验开关（写 `pwa_display_mode` cookie）切换。原话："要么给个开关吧，比如在设置里面可以让我自由选择要不要这种方式锁屏。"
2. 原话："第二，edge是直接看不见下方的进入按钮无法进入全屏模式"——Edge 打开站点停在开机页，底部那个圆形「进入」按钮整个看不见，连 App 都进不去；进了主屏反而正常。

**根因**：
1. 策略写死在代码里：`requestMobileImmersiveFullscreen()` 只有"锁得住/锁不住"两种自动行为，没有给人留一个显式偏好位。
2. **代码层（已实测到编译产物，端上复现为用户描述）**：开机页拿不到手机壳的保护变量。`--status-bar-drop` 是进 App 之后才由 `desktop-shell.tsx:4322` 挂到壳上的内联变量，开机页没有主题、取默认 `0px`；而 `styles/phone-shell.css` 的手机分支里 `.app-root.splash-root` 高度写的是 `100lvh`（地址栏收起后的**最大**高度），`html,body{overflow:hidden}`。Edge 走 `minimal-ui`（`app/manifest.webmanifest/route.ts` 对 Edge 特调）不请求全屏，地址栏常驻，实际可见高度只有 `dvh/svh`，底部那条差值被裁掉又滚不动，正好吃掉 `.splash-enter-button{bottom:36px}`（`styles/base.css`）。主屏正常就是因为主屏有 `--status-bar-drop` 上移。

**改了什么**：
- `lib/pwa-display-mode.ts`：新增策略位 `ImmersiveFullscreenPolicy = "auto" | "always" | "never"`，存 `localStorage["aiphone_immersive_fullscreen_policy"]`（SSR / 存储被禁 / 脏值一律回落 `auto`），切档派发 `aiphone-immersive-fullscreen-policy-changed` 事件。
  - `auto`＝上一轮的行为（实测一次，锁不住就判死不再请求）。
  - `always`＝总是请求全屏沉浸，**接受转横风险**：锁失败也不退出全屏，看门狗不再自动退出，`unsupported` 不拦请求（但 `portraitLockState` 仍如实记录，便于排查）。
  - `never`＝不请求全屏也不锁方向，且如果当前正在全屏里，靠事件监听**立刻 `exitFullscreen()`** 并把 `portraitLockState` 清回 `unknown`，切回 `auto` 后还能重新实测一次。
- `components/phone-theme-app.tsx`：主题 App → SYSTEM SETTINGS →「状态栏」弹窗里，原「显示系统状态栏」开关下方新增一行「全屏与方向锁」三选一 chips（自动 / 总是全屏 / 从不全屏），点击即写策略并给提示。入口与旧的 cookie 试验开关共存，互不覆盖（一个管 manifest 安装态，一个管运行时全屏请求）。
- `styles/phone-shell.css:1231-1258`：手机分支的 `.app-root.splash-root` 高度改贴可见高度——`height:100lvh` 保底后紧跟 `height:min(100dvh,100lvh)`，并把 `--phone-screen-height` 同步成 `min(100dvh,100lvh)`；另加 `.splash-enter-button{bottom:calc(36px + env(safe-area-inset-bottom,0px))}`。两条都带注释说明 Edge 那个现象，防止以后被"统一用 lvh"改回去。

**验证结果**：
- `npx tsc --noEmit` 通过（EXIT=0）。
- `perf-probe-local/orient-probe/fullscreen-lock.mjs`（Node 24 类型剥离直接跑源文件，stub `window/document/screen/navigator/localStorage`）：**36/36 断言通过**，新增覆盖 always 不退出全屏、never 不请求、看门狗在 always 下不退出、切到 never 立刻退出全屏并清零状态、默认 `auto`、脏值/无痕存储不炸。
- 浏览器实测（本机 dev `http://127.0.0.1:3011/`，turbopack）：「状态栏」弹窗里三档 chips 正常渲染；依次点 从不全屏 / 总是全屏 / 自动，`localStorage` 分别写入 `never`/`always`/`auto`，且高亮档（读元素内联 `style` 的 `font-weight: 600`）跟着点击实时移动，无需刷新。
  - 排查过程记一笔，别再误判：最初用 `getComputedStyle().backgroundColor` 轮询，以为"高亮不动、疑似脏渲染"，实际是 chips 上 `transition:0.2s` 让 600ms 内读到的是过渡中间色（`rgb(241,242,246)` 正是起始色）。**判断这类内联样式切换要读 `getAttribute('style')`，不要读计算样式。**
- 编译产物核对：dev chunk `_43f1b0f0._.css` 里手机分支 `.app-root.splash-root` 同时保留 `height:100lvh`（在前）与 `height:min(100dvh,100lvh)`（在后），源码顺序未被 Lightning CSS 打乱；`.splash-enter-button{bottom:calc(36px + env(safe-area-inset-bottom,0px))}` 也在产物里。桌面分支实测进入按钮 `bottom:36px`、`body overflow:visible`、`btnBottom 843 < innerHeight 849`，桌面没被这次改动弄坏。
- **未验证**（必须她在真机上看）：Edge 上开机页是否真的能看见进入按钮；`min(100dvh,100lvh)` 在国产壳的 `dvh` 实现偏差下是否仍留有一条被裁的缝；`always` 档在她那个拒绝方向锁的 PKS110 上是否等于"重新出现横屏"（按代码推断是的，这是她的显式选择而非回归）。
- 配套诊断件（**不入库**，存档 `D:\project\ai-virtual-phone-main\perf-probe-local\orient-probe\`）：探针升到构建 `2026-10-20.f`——开机页 `SplashScreen` 里也挂入口（只挂主屏的话，"进不去 App"这种卡法一条日志都拿不到），快照与日志新增「开机页度量」行（`底部被裁 = innerHeight − (visualViewport.offsetTop+height)`、按钮在 layout 视口内/在可视区内两个口径、`opacity`/`pointer-events`/`bottom` 求值、`--status-bar-drop` 取不到时如实报 null），日志头新增「全屏策略」。本机已验证：`check-enable.mjs` 26/26、`fullscreen-lock.mjs` 36/36、公共副本 3011 临时装探针后开机页入口实测渲染在 (77,727) 167×57 且度量行可读、`git apply`/`-R` 往返干净。**私有 dev 那份还停在 `.e`**，装 `.f` 要改 4 个文件（`lib/orient-probe.ts`、`components/orient-probe-bootstrap.tsx`、`components/main-app.tsx` 加 splash 挂载、`components/desktop-shell.tsx` 加 `site` 属性），等用户点头再动私有仓库。

**遗留与风险**：
1. `always` 是有意识地把转横风险交还给她，不提供"横屏可用"的适配——真正的横屏布局仍未做（她暂不做）。
2. 开机页这次只解决"按钮可达"，没做整页按可见高度重排；地址栏特别高的壳上仍可能出现上下留白或画面被压。
3. 策略是 `localStorage`，清站点数据 / 换浏览器回到 `auto`；而 `pwa_display_mode` cookie 走的是 manifest 安装态，两个开关语义不同，别合并。
4. 上一轮 A/B 期间本机点过「恢复/禁止全屏请求(试验)」，`pwa_display_mode` 可能仍是 `standalone`，这会抑制全屏请求——真机复测前要先清掉，否则 `always` 档看着像无效。

## 2026-10-20（晚）· 真机日志定性：全屏请求成功、方向锁被静默拒绝 → 改成"锁不住就不全屏"

**现象**：上一轮横屏分支修复上线后，用户仍报手机打开就躺倒、"只看得见一小截"。这次拿到真机探针日志（构建 `2026-10-20.e`，机型 PKS110 / Android 16），首次有端上实测数据。

**实测数据**（探针 `lib/orient-probe.ts` 快照，非桌面模拟）：
- `含横屏分支 1 条`、`mqMobileLandscape:true`、`mqMobilePortrait:false`、`shellRect 804x360` → 端上跑的确实是修复后的代码，横屏分支已命中，**没有再掉回 390×844 桌面舞台**。
- `inner=vv=screen=avail=804x360`、`dpr 3`、`phys 2412x1080`（804×3=2412、360×3=1080）、`scale=1.00` → 是设备真的转横，不是 layout viewport 被宽屏策略撑开（上一轮的缩放假设排除）。
- `fullscreen:"html"`（`document.fullscreenElement` 有值）+ `displayMode:"fullscreen"`，而同一次探测里 fetch 到的 manifest 是 `display:"standalone"`、`orientation:"portrait"`（463 字节）→ 页面处于**我们 JS 请求来的全屏**，且这个壳没有执行 manifest 的方向声明。
- `lockApi:"yes"` 只说明 API 存在；页面仍是横屏 → `lock("portrait")` 实际被拒绝，而旧代码用 `.catch(() => {})` 静默吞掉，全屏照留。

**根因**：`requestMobileImmersiveFullscreen()` 里"进全屏"和"锁竖屏"是两件独立的事，失败却不改变结果。全屏一开，浏览器地址栏这道最后的保护没了，方向交给壳自己的全屏方向策略（系统自动旋转关着也不受约束），锁又没锁上 → 390 竖屏稿被压进 360 高。上一轮条目里标"推测"的第 2 条浏览器层根因，这次拿到直接证据。

**改了什么**（`lib/pwa-display-mode.ts:84-167`）：
- `lockPortraitIfSupported()` → `tryLockPortrait()`：**把锁的结果如实返回**，不再吞失败。
- 新增模块级 `portraitLockState`（`unknown` / `locked` / `unsupported`）+ `getPortraitLockState()`：一次会话只实测一次。锁不上就记为 `unsupported`，后续点击不再请求全屏，避免"全屏→转横→退出→又全屏"来回抖。
- `securePortraitInsideFullscreen()`：全屏成功后 await 方向锁，**锁不住立刻 `exitFullscreen()` 退回浏览器态**——宁可露出地址栏，也不把她留在没法用的画面里。锁得住才享受沉浸。
- `requestMobileImmersiveFullscreen()` 增加僵局入口：进来就已是"横屏 + 全屏"（旧版本留下的状态）时，借这次用户手势补锁一次，锁不上就退出全屏。
- 新增 `bindLandscapeWatchdog()`：监听 `orientationchange` / `resize`，只要处于全屏且视口转横（覆盖"lock 报成功但不生效"那类壳），就判死并退出全屏。

**验证结果**：
- `npx tsc --noEmit` 通过（公共副本）。
- `perf-probe-local/orient-probe/fullscreen-lock.mjs`：Node 24 类型剥离直接 import 源文件打桩断言，**22/22 通过**（锁得住留全屏 / 锁被拒退出 / 无 lock API 退出 / lock 直接 throw 退出 / 僵局补锁两种结果 / Edge 不请求 / cookie=standalone 不请求 / 看门狗转横退出并判死 / 判死后不重试 / 竖屏 resize 不误伤）。
- 真浏览器核对 `perf-probe-local/orient-probe/browser-check/`：用 `module.stripTypeScriptTypes` 原样转译真实源文件、页面 import 后点按钮调生产函数。结果：桌面宽视口下正确地**不**请求全屏（宽高判定拦住的）；伪造竖屏后 `requestFullscreen` 确实被调用；伪造"全屏 + 转横"时看门狗调用 `exitFullscreen` 1 次且状态变 `unsupported`；判死之后再点不再请求。该宿主是 Electron，真实全屏请求的 Promise 一直 pending，**所以"进全屏后 Android 到底拒不拒 lock"这一条仍只能由真机回答**——但新代码不需要提前知道答案：锁得住就全屏，锁不住自动退回浏览器态，两条路都不会停在横屏全屏。
- **未验证**：真机装上这版之后是否还转横；退出全屏后壳会不会自己转回竖屏。

**遗留与风险**：
1. 若某壳**不看 manifest、也不接受 lock、还在非全屏态自己转横**，本次改动只保证不再出现"全屏横屏压扁"，画面仍是 804×360 的手机布局（铺满但按竖屏稿排布）。那种情况要单独做横屏可用或"请转回竖屏"闸门。
2. 锁不住的壳从此没有沉浸全屏（露浏览器地址栏），顶部留白仍按沉浸态的 80px 估算，会比实际需要的一宽。刻意**不**自动写 `pwa_display_mode=standalone` cookie：那个开关属于用户在设置里的选择，代码不去抢。
3. 止血开关照旧：设置里的「显示系统状态栏」写 `pwa_display_mode=standalone`，从此完全不请求全屏。探针面板的「禁止全屏请求(试验)」按钮写的是同一个 cookie，可以在旧构建上直接验这条扳机。

## 2026-10-20 · 横屏浏览器把画面掉回 390×844 桌面舞台，手机只剩一小截可用

**现象**：用户实测——同一站点，Chrome 手机正常，其他浏览器（国产壳/第三方 Chromium）打开后画面横向，且只能看到一小截内容，完全无法操作。手机系统自动旋转已关闭。

**根因**（两层，代码层已实测，浏览器层为推测）：
1. **代码层（已确认）**：手机布局的唯一入口是 `styles/phone-shell.css:1129` 的 `(max-width: 500px) and (hover: none) and (pointer: coarse)`。视口一转横，CSS 宽度变成 800+，`max-width: 500px` 失配，整页掉回 `styles/tokens.css:183` 的固定 390×844 桌面舞台（还套金属外壳）。844px 高的画面塞进 390px 高的横屏视口，就是"只剩一小截"。同一条媒体查询在 JS 里被复制了 4 份（`main-app.tsx:222`、`desktop-shell.tsx:970`、`android-fullscreen.tsx:16`、`use-call-keyboard-offset.ts:25`），横屏时一起失配。
2. **浏览器层（推测，未在你机器上实测）**：`main-app.tsx` 给 document 挂了 click 监听，每次点击都 `requestFullscreen()`（默认除 Edge 外全开，见 `lib/pwa-display-mode.ts` 的 `shouldRequestPwaFullscreen`）。网页进入全屏后方向不再受系统自动旋转开关约束，改由浏览器自己的全屏方向策略决定；Chrome 遵守传感器锁定，部分国产壳在沉浸态用 `sensorLandscape` 一类策略，于是只有 Chrome 竖着。仓库内不存在任何 `screen.orientation.lock` / manifest `orientation` / Android `screenOrientation` 锁方向的代码（已全库搜过），也没有对根容器做 90° 旋转。

**改了什么**：
- `styles/phone-shell.css:1129`：媒体查询改成逗号（Media Queries 3 的 or 语义）两条并列——原竖屏条件 + `(max-height: 500px) and (orientation: landscape) and (hover: none) and (pointer: coarse)`。横屏手机高度约 390 命中，平板横屏 600+ 不命中，继续走桌面舞台。刻意不用 `or` 嵌套分组：老内核解析不了整条查询会整条判 false，反而彻底丢掉手机布局。
- `lib/pwa-display-mode.ts`：新增 `MOBILE_PORTRAIT_MEDIA` / `MOBILE_LANDSCAPE_MEDIA` / `isMobilePhoneViewport()`，把上述两条查询收成单一事实源；新增 `requestMobileImmersiveFullscreen()`——请求前跳过"已在全屏"和"视口本来就是横向"（`screen.orientation.type` 优先，缺失时比宽高），请求成功后调 `screen.orientation.lock("portrait")`，iOS/无该 API 的环境 catch 掉不影响全屏。
- `components/main-app.tsx:221-232`、`components/android-fullscreen.tsx`：两处 click 全屏逻辑改用共享的 `requestMobileImmersiveFullscreen()`，删掉重复的 `shouldRequestPwaFullscreen` + `requestFullscreen` 裸调用。
- `components/desktop-shell.tsx:970/990`、`components/chat/use-call-keyboard-offset.ts:25`：换成 `isMobilePhoneViewport()`。键盘抬升那处原本用 MediaQueryList 快照，改成每次实时调用函数，避免横屏后拿到过期判定。

**验证结果**（turbopack dev @ localhost:3007，本机无真机）：
- `tsc --noEmit` 通过；`npm run build` 通过。
- 编译产物 `.next/static/css/c697367b0e2e31c7.css` 与 dev 运行时 `CSSRule.media.mediaText` 均确认横屏分支保留，未被 Lightning CSS 折叠或丢弃。
- `lib/pwa-display-mode.ts` 用 Node 24 类型剥离直接跑源文件做了 12 条断言（竖屏/横屏/桌面平板判定、横屏跳过请求、竖屏请求后锁 portrait、已全屏不重复请求、standalone 偏好不请求、Edge 不请求、无 lock API 时仍请求且不抛错）：12 passed / 0 failed。测试脚本在临时目录，未入库。
- 桌面视口回归：3007 首页正常渲染，控制台无报错（只有 React DevTools 提示与 Fast Refresh 日志）。
- **未验证**：真机上横屏是否真的消失、国产壳是否接受 `lock("portrait")`。这两条要你在出问题的那个浏览器上实测。

**遗留与风险**：
1. 横屏命中手机布局后，画面按 100vw×100lvh 铺满，但内部图标/网格仍按 390 设计稿的 px 尺寸，横屏会出现左右留白——这是"能用但不好看"的兜底，不是横屏适配。真要横屏可用得单独做一套布局。
2. `@media (max-width: 373px)` 的窄屏等比缩放分支只在竖屏生效，横屏不走。
3. 若某浏览器既不遵守 lock、又在进入全屏后强制横屏，则本次改动只保证"不再掉回桌面舞台"，方向仍由浏览器决定。止血开关是设置里的「显示系统状态栏」（写 `pwa_display_mode=standalone`，从此不请求全屏）。
4. 其他 CSS 里的手机相关查询没有横屏分支（`components.css:4569` 用的是不带宽度的 `(hover: none) and (pointer: coarse)`，横竖屏都命中，不受影响）。

## 2026-10-19 · 快捷操作面板：不再压在控制坞上；dev 里毛玻璃失效的真实原因（手写 -webkit- 前缀被折叠）

**现象**：从坞里点「快捷切换」弹出的面板（1）整块盖在坞条按钮上，只露出上下两颗；（2）桌面时钟 / 图标直接透过来，字看不清。

## 2026-10-19 · 退出等待约 5 秒：加返回遮罩 + 真机自记录性能探针（临时件）

**现象**：上一条改动把开发机的退出耗时从 540~600ms 压到 48~66ms，但用户真机实测仍要等约 5 秒，而且期间界面完全没反应 —— 分不清是卡住了还是在加载。

**关键事实**：开发机（Chrome / 20 核桌面 CPU）和手机 WebView 差一个量级，两端数字不可互推。没有端上数据就只能猜，所以这次先做测量件，不做无依据的优化。

**改了什么**：
1. `components/desktop-shell.tsx`：退出遮罩 `.app-exit-veil`（「正在返回桌面…」）。在 `pointerdown` 的**捕获阶段**挂 `is-on` class —— React 的 `onClick` 要等 pointerup 之后才跑，中间至少隔一帧，这样样式变更能在主线程被占住之前交给合成器；CSS 用 `transition: opacity 160ms linear 220ms`，**显形有 220ms 延迟**，快的设备一帧就画完桌面、遮罩来不及出现，不会闪。收回走双 rAF + 400ms 定时器兜底 + 10s 保险。
2. `lib/perf-probe.ts`（新）：真机自动记录，不需要控制台。记 boot 环境（UA/DPR/CPU 核数/deviceMemory/构建标识）、kv 各键体积、`navigator.storage.estimate()`、App 切换、所有 ≥80ms 的 longtask、主线程看门狗（setInterval 漂移 >400ms）、前后台切换。日志存 kv 键 `perf_probe_log_v1`，环形 400 条，刷新不丢。
3. `components/perf-probe-panel.tsx` + `styles/phone-shell.css` 的 `.perf-probe-*`：左下角「日志」浮钮 → 面板，可 导出文件 / 复制全文 / 刷新 / 清空。导出用 `lib/download-utils.ts` 的 blob 下载（和备份导出同一条已验证路径），复制走剪贴板 + `execCommand` 兜底。

**验证**：`tsc --noEmit` 通过；Fast Refresh 无报错；桌面/特调开合后遮罩正确显形并收回；面板能出摘要与原始事件；清空生效；日志跨刷新累积（boot=2）。
**未验证**：遮罩在"主线程真被占住 5 秒"时到底画不画得出来 —— 后台页 CSS 过渡不推进，开发机测不了。为此加了 `transitionend` 探针，真机日志里出现 `note/veil-painted` 才算证实；没出现就说明合成器这条路在 WebView 上不成立，得换成"先画遮罩再分帧做重活"的方案。**（2026-10-19 同日已由用户真机日志证实：`veil-painted` 出现在点关闭后 403~569ms，见最上方条目。）**

**踩到的坑（已修）**：
- 后台页 `setInterval` 被钳到 1s，看门狗把节流误报成 193 条 750ms "卡顿" → 现在 `document.hidden` 时直接不判定，摘要里也打印当前可见性。
- 只用双 rAF 收遮罩，在后台页 rAF 不触发 → 遮罩永久留在屏幕上（实测 `veilAfter: true`）→ 加 400ms 定时器兜底。
- 未水合时写日志会用空数组覆盖真日志 → `persist()` 前先 `isKvHydrated()`。

**拆除方式**：删 `lib/perf-probe.ts`、`components/perf-probe-panel.tsx`，去掉 `desktop-shell.tsx` 里 `perfProbe` / `PerfProbePanel` / `startPerfProbe` 的引用（遮罩本身可以留，只删探针调用），再删 `phone-shell.css` 的 `.perf-probe-*` 段落。`.app-exit-veil` 属于正常功能，不拆。

## 2026-10-19 · 退出 App 卡顿：桌面改为常驻挂载 + CSS 隐藏

**现象**：从任何 App 返回桌面都会卡住半秒以上，聊天、独家特调最明显。用户反馈"打开和关闭都卡"。

**测试条件（重要，换条件数字不可直接比）**：`npm run dev`（turbopack，localhost:3001），真实导入数据 —— 桌面 27 图标 / 8 组件 / 4 Dock；IndexedDB 实测 `AiPhoneKvDB` 72 条 / 33.9MB（其中 `mixology_sessions_v1` 14.3MB、`ai_phone_api_logs_v1` 16.3MB），主题库 169 资产 / 62.6MB（含 14.2MB 字体、2.7–4.6MB 图标皮肤），聊天库 77 消息 / 5 会话。探针：`tools/exit-lag-probe-chat-mix.js`（长任务 + 主线程阻塞 + DOM 就绪时刻 + `JSON.parse/stringify` 钩子；`tools/exit-lag-probe.js` 是桌面渲染 A/B 版。两者是本地诊断脚本，贴到浏览器控制台跑，不入库）。

**实测数据**：

| 场景 | 改造前 | 改造后 |
|---|---|---|
| 退出 App → 桌面图标挂好（前台，同数据） | 291–308ms（React 重挂）+ 245–289ms（首帧栅格化），单帧最长 246–343ms | 48–66ms，单帧最长 23–35ms |
| 退出 App（后台页 A/B，同一次会话内先后跑，条件一致） | DOM 392–467ms，长任务 392+404 / 466+418 | DOM 62–74ms，长任务 62–74 |
| 打开 聊天 | DOM 19–22ms，无长任务 | DOM 82–88ms，长任务 53ms |
| 打开 独家特调 | 长任务 69–75ms，2–3 次 >1MB `JSON.parse` | 长任务 96–120ms，2 次 >1MB `JSON.parse` |

**根因**：`components/desktop-shell.tsx` 里桌面与 App 正文互斥渲染（`{!activeApp ? <桌面> : <App>}`，Dock 同样 `!activeApp` 条件渲染），退出时桌面整棵树（30 多层 `backdrop-filter` 毛玻璃 + 图标皮肤图）被卸载后重新挂载，产生两条背靠背长任务。与是哪个 App 无关 —— 聊天和特调的退出数字一致。

**改了什么**：
- `components/desktop-shell.tsx`：桌面图标层 + 分页圆点包进 `.phone-desktop-layer`，Dock 的 `<footer>` 都改为常驻渲染；App 打开时给它们加 `inert` + `aria-hidden`。
- `styles/phone-shell.css`：新增 `.phone-desktop-layer`（flex 列，占满工作区），并在 `.phone-workspace.app-open` / `.phone-shell.app-open-shell` 下对桌面层与 `.dock` 设 `display: none`。
- 同日的另一处：`.phone-wallpaper` 的 `transition: opacity 220ms ease` 改为 `none`。原因是壁纸淡入只在"返回桌面"时触发（打开 App 时被 `transition-duration: 0s !important` 瞬时隐藏），淡入的每一帧都会让全部毛玻璃重新采样背景。把淡入拉长到 2s 同样降到 27ms，证明成本是"逐帧重模糊"而非一次性栅格化。

**验证**：`tsc --noEmit` 通过；前台截图确认桌面（图标皮肤 / 组件 / 分页点 / Dock）与 App 全屏态均正常；退出后 `.phone-desktop-layer` 回到 `display:flex`、Dock 回到 `grid`；分页圆点切页 transform 正常；控制台无新增报错。

**遗留与风险（下次接着做之前先看这里）**：
1. **打开 App 变慢了约 40–60ms**：常驻后"挂 App + 把桌面从布局里摘掉"落在同一帧。收益（退出省 250–500ms）明显大于代价，但这条要继续优化，不能当作没发生。
2. **App 打开期间桌面树常驻**：桌面 state 变化会连带重渲染桌面子树。音乐浮层早已隔离（见 `desktop-shell.tsx` 中 `MusicShellOverlays` 上方注释），但后续若发现"App 内操作变卡"，第一个要怀疑的就是这里。
3. **独家特调打开的 14MB 整包解析没动**：`lib/mixology/storage.ts` 的 `readJson` 对 `mixology_sessions_v1` 做整串 `JSON.parse`，`writeJson` 整串 `JSON.stringify`；`components/mixology/mixology-app.tsx:127` 在 `useState` 初始化里同步调 `loadMixSessions()`。要修得拆存储结构，属于独立一次改动。（已由同日最上方的 readJson 备忘条目部分解决：重复 parse 消除了，整包 stringify 仍在。）
4. **聊天没复现打开卡顿**：本机聊天库只有 77 条消息，量级不够。代码侧同类隐患在 `lib/chat-storage.ts:997` `hydrateChatStorage()`：`chatDb.messages.toArray()` 全量取行（含内联 base64 附件，未剥离），随后 `refreshSessionPreviewMetadata` 对每个会话全量排序，O(会话数 × 消息数 log n)。用户真实数据更大时才会成为主角。
5. **`ai_phone_api_logs_v1` 16.3MB**：`lib/api-log-store.ts` 每发一次 LLM 请求就整包 parse + stringify（`_loadLogs:50` / `_saveLogs:58`），调用点 `chat-engine.ts:922` 等。这是独立的第三个问题。

## 排查这类问题时的固定坑（每次都要先确认）

- **空数据下测性能等于没测**。先量化数据规模（各库条数、字节数），把规模和计时一起写进结论。
- **页面在后台时帧率测不出来**。`document.hidden` 为真时 rAF 不触发、渲染任务被跳过，`setTimeout` 被钳到 ≥1s，长任务只剩脚本部分。要么把窗口切回前台，要么改用 MessageChannel 主线程阻塞采样，并且必须在结论里注明条件；**同一组 A/B 要在同一种可见性状态下跑**。
- **改了内联脚本先 `node --check` 再 build**，否则白屏会被误判成"数据丢了"。
- **跑 `npm run build` 前先停掉 turbopack dev server**：两者共用 `.next`，并发会把 dev 打成连续 500（2026-10-19 实测踩过，恢复方式是停 dev → 干净 build → 重启 dev）。
- **真机探针不在仓库里**：存档在 `D:\project\ai-virtual-phone-main\perf-probe-local\`，要测端上性能先按那里的 README 装回来（`git apply -R unwire.patch`），别再重新手写一遍。
- **自定义 App 沙盒**：`sticky` 定位、`backdrop-filter` 会触发 503；宿主 API 不支持 doc/docx 解析。
- **已安装 App 是 HTML 快照**：改源文件或重打 zip 不会自动生效，必须换包或重装并升 manifest 版本。
- **`saveMeta` 必须带 `customTemplates` 字段**（随想笔记），漏了会静默丢模板。
- **禁止在 `bind()` 里给条件渲染的元素绑事件**，要在 render 内绑或用事件委托。
