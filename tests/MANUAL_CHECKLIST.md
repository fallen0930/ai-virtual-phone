# 手动确认清单

这里只放**自动化测试覆盖不到**的项目。`tests/` 里的用例全部跑在 Node + fake-indexeddb，
`lib/kv-db.ts` 的 `hydrateKvDb()` 被 `typeof window === "undefined"` 守卫短路，
所以「写进真实 IndexedDB、刷新页面后还在」这类事必须由人在浏览器里确认。

约定：每确认一项，把 `[ ]` 改成 `[x]` 并在后面写上确认日期。

## 三、卡片来源与丢弃归档（本轮新功能）

自动测试覆盖了函数本身的行为。**「重说」这条路径已有端到端自动覆盖**
（`tests/narrative-generate-source.test.ts` 真 import `mixology/engine`，只 mock 大模型入口与 API 配置读取），
但**回溯 / 编辑截断 / 撤回**三处仍然只有函数级测试、没有接入验证，需要在浏览器里逐条走一遍：

- [ ] **3.1 重说**：抽出一张卡后点「重说」。期望：旧回复的卡变为「归档」，
  归档原因是「来源回复已被丢弃（重说）」一类文案；新回复抽出的卡为「生效」；
  生效列表里不存在同一来源的两张卡。同时确认小票/机括记住的值照常回滚，没被这次改动带坏。
  注：这一条**已有自动测试覆盖**（`tests/narrative-generate-source.test.ts` C 走真实 `rerollMixReply` 端到端），
  但仍建议真机确认一次——自动测试里的小票与机括是空材料，真实配方在小票落账后的回滚只有浏览器能验。
- [ ] **3.2 回溯**：回溯到中间某条消息。期望：其后所有 assistant 回复抽出的卡归档；
  来源未知的卡（记忆整理/补抽历史/深度抽取产的）一张都不动。
- [ ] **3.3 编辑玩家发言（后续轮次原文齐全，可回放）**：期望一张卡都不归档
  —— 后续轮次是原地重画，消息 id 没变。
- [ ] **3.4 编辑玩家发言（后续有老轮次没存原文，不可回放被截断）**：
  期望被截断掉那些轮的卡归档。
- [ ] **3.5 继续生成 / 重新生成尾部**：期望不归档任何卡（这两条路径纯追加，不删消息）。
- [ ] **3.6 换开场白、按新滤网重洗历史**：期望不归档。
  这是**已知限制**：这两处只换正文、消息 id 不变，卡仍指向那条活着的消息。
  编辑某条助手回复的正文同理（`editMixTurn` 保留 id），也不归档。
- [ ] **3.7 撤回最后一轮**（`undoMixLastRound`）：**目前无入口，无法手测**，
  函数本身的归档行为由 `tests/card-source.test.ts` 覆盖；等 UI 接上后再补手测。
- [ ] **3.8 归档卡的恢复**：在「已归档」筛选下点「恢复生效」。期望：卡片回到「生效」、
  归档原因被清除；来自被丢弃回复的卡旁边应能看到小字提示「该卡来自已被丢弃的回复」；
  悬停在归档卡上能看到「归档原因：……」。已归档的卡不再显示 📦 按钮（重复归档无意义）。
  注意：情感卡列表只渲染前 8 条，归档的情感卡要先点「已归档」筛选才看得到。
- [ ] **3.9 竞态**：出一轮回复后立刻（在抽取还没结束时）点重说。
  期望：慢了一步落库的那张卡直接是「归档」，不会以「生效」混进上下文。
- [ ] **3.10 水位不回退**（本轮有意不做，见待办 #24）：重说后关系水位停在旧回复推上去的值，
  确认你接受这个现状；只验证「来源已消失时不再写水位」。
- [ ] **3.11 执笔生成后点重说**（本轮修复待办 #25）：在执笔面板选定报幕生成正文、正文进入对话之后，
  到对局页面点「重说」。期望：执笔那条回复抽出的卡变「归档」（原因写「来源回复已被丢弃（重说）」），
  新回复抽出的卡「生效」，**生效列表里不再残留来源未知的重复卡**。
  顺带看一次 DevTools Network：这一次点击应当是 1 次正文生成 + 1 次抽取（改动前是 1 + 2）。

## 四、批量执笔的并发（本轮只观察，不加锁）

- [ ] **4.1 批量生成缓冲区的落库结果**：往缓冲区放 3 条以上报幕，点「批量生成」。
  期望仍然是一张一张进对话，但**后台抽取任务是并行的**：请确认事后翻记忆卡时
  没有看到同一主题两张几乎一样的卡、也没有看到水位停在奇怪的值。
  这一项是为了观察「多任务同时写同一会话」在真实使用里到底会不会出问题（现状说明见本轮汇报）：
  批量缓冲区里每条都是「生成 → 插入 → 后台热抽」，**上一个抽取还没跑完，下一条就已经插入**，
  所以同一会话里同时挂着多个抽取任务是设计现状，本轮不加锁。

## 五、audience 认知隔离（本轮新功能）

自动测试（`tests/audience-isolation.test.ts`，8 个用例）覆盖了函数与拼装层的行为：
写入侧规范化、写正文按角色过滤、走向卡改为导演视角（知情标注 + 排除现实层 + 5+3 上限 + 红线）。
**提示词改了之后模型的行为只能看产出**，以下需要在浏览器里真机走一遍：

- [ ] **5.1 走向卡吃得到全场信息**：抽出一批分别标着「仅某角色知情」「仅玩家知情」「系统预埋」的卡，
  点生成走向卡。期望报幕里**允许**利用这种信息差（例如"只有玩家知道的那件事可以做成伏笔"），
  而选定这条报幕生成正文后，角色**不会**把「系统预埋·未揭示」的设定当作已经揭示的事实写出来，
  也不会说出只有玩家知道的事。
- [ ] **5.2 现实层的卡不掺进剧情**：在戏外聊天状态（非剧情模式）下产生的「现实层」记忆卡，
  不应该出现在走向卡的素材里（面板里勾"现实层"能看到这些卡）。
- [ ] **5.3 新抽出的卡落盘值已规范化**：抽一轮后在 DevTools → IndexedDB 里查
  `narrative:{会话id}:memory:{卡id}`，`audience` 里**不应再出现** `"narrator"`；
  模型给的 `"character"` 应已被换成当前角色的名字；缺失/乱值应是 `["all"]`。
- [ ] **5.4 角色改名后的失配（已知限制，确认你能接受）**：把角色卡改名再进对局，
  用**旧角色名**标注的卡不再进入正文上下文（角色看不到），但走向卡那份仍然带着
  `[仅旧名知情]` 的标注（导演看得到）。这就是本轮有意接受的限制，稳定标识见待办 #28。
- [ ] **5.5 面板看不到 audience**：面板的卡片列表不显示、也不能编辑知情范围，
  只能靠抽取器给的判断（待办 #29）。确认这个现状不挡你玩。

## 七、待核卡参与走向卡（本轮新功能）

自动测试（`tests/pending-cards-in-director-context.test.ts`，8 个用例）覆盖了拼装与入库层的行为：
导演上下文含待核卡并标「（未确认）」、待核只占剩余名额（记忆 ≤3 / 情感 ≤1）、按置信度排序、
角色上下文一律排除非生效卡、`confirmAllPendingCards` 的口径、入库状态门槛。
**状态门槛改的是"哪些卡会自动生效"，这条一定要在真机上看一遍**：

- [ ] **7.1 低置信与世界变更确实停在待核**：正常玩几轮，让执笔/特调自动抽一批卡，
  打开面板看「待核实」数量。期望**置信度不够的卡和世界变更卡都是待核而不是生效**
  （本轮之前它们会直接生效）。逐条点开确认前，角色正文里不应引用这些卡。
  记忆整理（压缩）那条链产出的卡本来就 100% 待核，行为不变。
- [ ] **7.2 整理记忆后生成走向卡，看待核卡占比**：跑一次记忆整理产出一批待核卡，
  然后点生成走向卡。期望走向卡能提到那些还没核的线索（报幕里出现待核卡的内容方向），
  但**选定报幕生成的正文**里，角色不会把「（未确认）」的卡当既定事实复述。
  待核卡很多时，它们在素材里最多占记忆 3 条、情感 1 条——生效卡多时可能一条都看不到，属正常。
- [ ] **7.3 批量确认按钮与弹窗文案**：有待核卡时，筛选行「⚠️ 待核实」右边会出现
  「✅ 全部确认 (记忆 n / 情感 m)」。点下去应弹确认框，写明
  "确认后这 n 张卡将进入正文上下文，角色会把它们当作已知事实使用"。
  取消不动任何卡；确认后统计栏「待核实」归零、这些卡出现在「生效中」计数里，
  归档/冲突/陈旧的卡数量不变；切到**另一场对局**确认它的待核卡没被顺带清掉。
- [ ] **7.4 统计口径已统一**：顶部「待核实」与筛选行「⚠️ 待核实 (n)」应是**同一个数**
  （记忆 + 情感合计），本轮之前顶部只数记忆卡。
- [ ] **7.5 待核卡不进正文**：面板里留一张内容很显眼的待核卡（比如写明一个只有玩家知道的地点），
  不确认直接生成正文，期望正文里查不到这个细节。
- [ ] **7.6 覆盖不到的项**：「引擎各条路径是否真的调用了对应函数」（例如特调正常回复那条链
  仍然完全不读记忆卡，本轮没改）在 Node + fake-indexeddb 里测不到，只能按 2.x/7.x 在浏览器确认。

## 八、线索卡与伏笔卡（本轮新功能）

自动测试（`tests/thread-foreshadow-cards.test.ts` 18 个用例，另扩展了
`fork-copy` / `delete-purge` / `pending-cards-in-director-context`）覆盖了：抽取入库与同名合并、
导演上下文名额与标注、角色上下文一条不含、标记解析/剥离/回写、插入失败不回写、
丢弃归档、散落线头迁移、批量确认扩到四类。以下几条只能人在浏览器里看：

- [ ] **8.1 对局里看不到机器标记**（红线，最重要）：走一次「生成走向卡 → 选一条带
  `[推进:…]` / `[回收:…]` 的候选 → 选定报幕生成正文」。期望聊天流里的报幕行**干净**
  （只有 `（基调：…｜场景：…｜走向：…）`），聊天记录、导出文本里都查不到方括号标记。
  标记只应出现在**候选列表那一步**——那一条要原样留着才能回写，属于设计内的可见。
  如果聊天里出现了标记，说明剥标记的链路被绕过了，立刻回报。
- [ ] **8.2 回写确实发生了**：接 8.1，采纳后打开面板「悬念台账」，期望那条线的
  状态变成标记里写的新状态、"第 n 轮推进"的 n 变大、"最近"一句话就是标记里的变化。
  对不上号的那条（模型写了台账里不存在的线索名）应当**什么都不变**，
  浏览器控制台里有一条 `采纳回写忽略一条 [推进] 标记` 的 warn。
- [ ] **8.3 抽取器是否真的按"同名输出"表达进展**：这条只能看产出，Node 里 mock 掉的
  是模型本身。正常玩几场带悬念的剧情，观察台账里有没有"同一条线两张卡"（改名造成的重复）。
  重复多就说明提示词那句"用同名输出"没起作用，需要回来调提示词或加别名合并。
- [ ] **8.4 回写反映的是报幕的计划，不是正文实际内容**（已知限制，非缺陷）：
  报幕说这条线升到"爆发"、正文却只写了一点苗头，台账依然记成"爆发"。
  请核对这个偏差你能接受——真要按正文判定，得让正文自己带标记或事后复判，成本另计。
- [ ] **8.5 面板编辑四类操作**：线索「改状态」四态轮转（潜伏→升温→爆发→收束）、
  「改下一步」用输入框改文案、待核「✅ 确认」只把这张卡放进**导演**上下文
  （确认后再抽一次卡，正文仍不该引用这条线的内容）、「归档」「删」分别让卡片从台账消失 /
  彻底删除。伏笔的「标为已收」同理，且已收的伏笔不再出现在导演上下文里。
- [ ] **8.6 弹窗四类数量分开**：待核卡里同时有记忆与线索时，「✅ 全部确认」按钮应显示
  `(记忆 n / 情感 m / 线索 k / 伏笔 p)` 四个数，弹窗正文分两段写清
